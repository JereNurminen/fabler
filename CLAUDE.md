## Project Overview

Fabler is an interactive fiction (CYOA - Choose Your Own Adventure) creation tool built with Tauri. The application consists of:

- **Frontend**: React + TypeScript + Vite + Tailwind CSS + Headless UI
- **Backend**: Rust + Tauri + SQLx (SQLite)
- **Shared types**: Rust structs with TypeScript bindings via specta/tauri-specta

## Common Commands

### Development

```bash
# From creation-tool directory
cd creation-tool
yarn dev              # Start Vite dev server (port 1420)
yarn tauri dev        # Run full Tauri app in development mode
yarn build            # Build frontend
yarn tauri build      # Build complete Tauri application
```

### Testing

```bash
# From creation-tool directory
cd creation-tool
yarn test:e2e         # Run Playwright E2E tests (requires backend running)
yarn test:e2e:ui      # Run E2E tests in UI mode
yarn test:e2e:headed  # Run E2E tests in headed browser mode
```

### Database

- Database location: App data directory (`app_data_dir()/story_nodes.db`)
- Migrations run automatically on startup using `sqlx::migrate!`
- Debug menu includes "Reset database" option
- Migration files: `creation-tool/src-tauri/migrations/`

### Type Generation

TypeScript bindings are auto-generated from Rust types:

- Generated by `tauri-specta` in `main.rs` on build
- Output: `creation-tool/src/bindings.ts`
- Shared models in `shared/src/models.rs` use both `specta` and `ts-rs`

## Architecture

### Workspace Structure

This is a Cargo workspace with two members:

1. **`creation-tool/src-tauri`**: Main Tauri application backend
2. **`shared`**: Shared types and models (used by both Rust backend and TypeScript frontend via specta/ts-rs). Contains `models.rs` (core types) and `export.rs` (TOML export types).

The `engine` directory is a placeholder and not currently in use.

### Data Model

Core entities (defined in `shared/src/models.rs`):

- **Story**: Full story with all page content (id, title, pages[], start_page)
- **StoryOutline**: Lightweight story outline (id, title, pages: PageListItem[], start_page) - used for sidebar
- **Page**: Full page data (id, story_id, name, body, options[], flag_operations[])
- **PageListItem**: Minimal page info (id, name) - used in sidebar listing
- **Choice**: Option linking to another page (id, page_id, text, target_page, flag_operations[], conditions[])
- **Flag**: Boolean flag for conditional logic (id, story_id, name, default_value)
- **FlagOperation**: State change on a flag (id, flag_id, operation: "set_true"/"set_false"/"toggle")
- **ChoiceCondition**: Visibility rule for a choice (id, flag_id, required_value)
- **StoryListing**: Lightweight story representation (id + title) - used for story list

Export types (defined in `shared/src/export.rs`):

- **ExportedStory**: TOML-serializable story with metadata, flags[], pages[]
- **StoryMetadata**: id, title, start_page

Database schema:

- `stories`: Main story metadata with foreign key to start page
- `pages`: Story content nodes, belongs to story
- `choices`: Navigation options within pages
- `flags`: Boolean flags per story (unique on story_id + name)
- `choice_flag_operations`: Flag state changes triggered by choosing an option
- `page_flag_operations`: Flag state changes triggered by visiting a page
- `choice_conditions`: Visibility conditions for choices based on flag values
- All deletions cascade

### Frontend Architecture

**State Management** (Jotai):

- Uses Jotai for atomic state management
- **Core atoms** (`src/atoms/storyAtoms.ts`):
  - `currentStoryIdAtom`: Tracks which story is currently loaded
  - `storyOutlineAtom`: Async atom that loads lightweight story outline
  - `pageAtomFamily`: Atom family for individual page caching (loads full page content on demand)
  - `allPagesAtom`: Derived atom for array of page list items (id + name only)
  - `storyRefreshAtom`: Counter incremented to force outline refetch
  - `storyFlagsAtom`: Async atom returning Flag[] for the current story
- **Action atoms** (`src/atoms/storyActions.ts`):
  - Story: `loadStoryAtom`, `patchStoryAtom`
  - Pages: `getPageAtom`, `patchPageAtom`, `createPageAtom`
  - Choices: `createChoiceAtom`, `deleteChoiceAtom`, `patchChoiceAtom`
  - Flags: `createFlagAtom`, `patchFlagAtom`, `deleteFlagAtom`
  - Flag operations: `setFlagOperationAtom`, `removeFlagOperationAtom`
  - Conditions: `setChoiceConditionAtom`, `removeChoiceConditionAtom`
- **Hook** (`src/atoms/useStoryAtoms.ts`): Provides unified API for components
- Async atoms throw promises → triggers Suspense boundaries
- Errors caught by ErrorBoundary component

**Suspense & Error Handling**:

- Global Suspense boundary in `main.tsx` with `LoadingSpinner` fallback
- Additional Suspense around `PageCard` for per-page loading states
- `ErrorBoundary` component catches async errors from atoms

**Routing** (using `wouter`):

- `/` - Start page (story selection/creation)
- `/story/:story` - Story editor without specific page
- `/story/:story/page/:page` - Story editor with specific page selected

**API Layer**:

- `api.ts` wraps commands from `bindings.ts`
- Returns `Result<T, E>` type for error handling
- Backend commands invoked via Tauri IPC (or HTTP API when `VITE_USE_HTTP_API` is set)
- Atoms handle Result unwrapping and throw errors on failure

**Internationalization**:

- **All user-facing strings must go in `src/i18n/translations.ts`** — never hardcode text in components
- Use `const { t } = useTranslation()` in components to access translations
- For non-component contexts (e.g. Suspense fallbacks), import `translations` directly
- Translation keys organized by category: buttons, labels, placeholders, headings, status, emptyStates, conditions, operations, badges, alerts, errors
- Dynamic strings with interpolation go in the `dynamic` section as functions
- When adding new UI text, add the key to `translations.ts` first, then reference it in the component

### Backend Architecture

**Database** (`creation-tool/src-tauri/src/db/`):

- `Database` struct wraps `SqlitePool` (`mod.rs`)
- Split into sub-modules: `stories.rs`, `pages.rs`, `choices.rs`, `flags.rs`
- All queries use sqlx with compile-time verification
- Patch structs (`PagePatch`, `ChoicePatch`, `StoryPatch`, `FlagPatch`) allow partial updates
- Patch/create models defined in `creation-tool/src-tauri/src/models/mod.rs`

**Commands** (`creation-tool/src-tauri/src/main.rs`):

- All Tauri commands annotated with `#[tauri::command]` and `#[specta::specta]`
- **Stories**: get_stories, add_story, get_story, get_story_outline, delete_story, patch_story, export_story_toml, get_toml_schema
- **Pages**: get_page, patch_page, create_page
- **Choices**: create_choice, delete_choice, patch_choice
- **Flags**: get_story_flags, create_flag, patch_flag, delete_flag
- **Flag operations**: set_flag_operation, remove_flag_operation, get_choice_flag_operations, get_page_flag_operations
- **Conditions**: set_choice_condition, remove_choice_condition, get_choice_conditions
- Database setup happens in app setup hook, creates db directory if needed

**Export**:

- TOML export via `export_story_toml` command
- Schema template via `get_toml_schema` command (defined in `schema.rs`)
- Frontend uses Tauri dialog/fs plugins for save dialog

**Menu System**:

- Edit menu: Standard cut/copy/paste
- Debug menu: Database reset (emits "database-reset" event to frontend)

### Type Sharing Between Rust and TypeScript

The project uses two complementary systems:

1. **tauri-specta**: Generates TypeScript types and command wrappers from Tauri commands
2. **ts-rs**: Generates TypeScript types from Rust structs (via `#[derive(TS)]`)

All shared models derive both `Serialize`, `Deserialize`, `Type` (specta), and `TS` (ts-rs).

## Development Workflows

### Adding a New Page Field

1. Update `Page` struct in `shared/src/models.rs`
2. Create migration in `creation-tool/src-tauri/migrations/`
3. Update database queries in `db/pages.rs` (both read and write operations)
4. Update `PagePatch` struct in `creation-tool/src-tauri/src/models/mod.rs` if field should be patchable
5. TypeScript types regenerate automatically on next build
6. Update UI components as needed

### Adding a New Tauri Command

1. Implement function in `main.rs` with `#[tauri::command]` and `#[specta::specta]`
2. Add to `collect_commands![]` macro
3. Add to `.invoke_handler(tauri::generate_handler![])` macro
4. Bindings regenerate on next build
5. Use from frontend via `commands.yourNewCommand()` from `bindings.ts`

### Database Migration

- Migrations use raw SQL in `creation-tool/src-tauri/migrations/`
- Format: `YYYYMMDDHHMMSS_description.sql`
- Applied automatically via `sqlx::migrate!("./migrations")` on app startup
- Use transactions for complex migrations to maintain consistency

### Styling

- Uses Tailwind CSS for utility-first styling
- Headless UI (`@headlessui/react`) for accessible UI primitives (dialogs, transitions)
- Heroicons for icons
- `clsx` for conditional class composition
